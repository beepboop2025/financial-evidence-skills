# Financial Evidence 0.1.16 candidate

Prepared 28 October 2026. **Not yet published or independently verified as a
public release.** The last verified package is
[0.1.15](0.1.15.json). Existing PyPI/tag install links and published OCI digests
remain on their verified versions until new publication and consumer receipts exist.

## Changes

- Add `financial-evidence connect` to select existing public-research products
  and generate client-neutral `mcpServers` and VS Code `servers` configurations.
- Add a declared institution/workspace profile, explicit hosted-egress approval,
  source-rights review, destination checks, subscription inventory and hashed
  output receipts. Generation is offline and refuses existing output paths.
- Document which products and platform routes support current institutional
  research tasks, and distinguish those routes from private-silo capabilities.
- Record the bounded 28 October Windows Excel operator test separately from the
  earlier web test; include the native screenshot and updated Microsoft reviewer
  material. The Office runtime and manifest remain unchanged.

The connection generator does not enforce subsequent client request contents,
server-side institution isolation, real vendor entitlements, retention/deletion
or regulatory compliance. It does not connect an external subscription or private
institution system. Marketplace submission and approval are separate from this
software release.

## Candidate identity

The Python package, source MCP server, MCP bundle, OCI/PyPI registry declarations,
Gemini extension, Claude/Codex plugins, source catalogs and FDC3 metadata identify
`0.1.16`. The current and versioned MCP contracts preserve the same three-tool
schemas; only the package server version changes. Workspace, hosted products,
Office manifests, npm packages and Homebrew have their own version histories.

The root citation identifies the candidate without a release date or a claim
that the future tag exists. The integration and marketplace catalogs retain
`last_verified_release: 0.1.15` and use `release_state: candidate`. Historical
release receipts, published-image tests and digests remain unchanged.

For local source installation, use the
[connection guide](../connect/institution-portability.md). A generic install of
published version 0.1.15 does not provide the new command.

## Checks before a signed release

From a reviewed checkout, run the repository contract suites and deterministic
package checks. Put build environments and retained artifacts in the designated
development workspace.

```sh
python3 -m unittest discover -s tests -v
node --test tests/*.test.js tests/*.test.cjs
python3 scripts/build_office_kit.py --check
python3 scripts/build_excel_office_addin.py --check
python3 scripts/build_google_office_addon.py --check
python3 scripts/build_product_plugins.py --check
```

The existing `release-container.yml` workflow re-runs Python/Node contracts and
requires all of the following before publishing:

1. An SSH-signed release commit and tag trusted by
   `ops/release/financial-evidence.allowed_signers`. The tagged commit must equal
   the current `origin/main` commit; each checked manifest must match `v0.1.16`.
2. The pinned remote Worker source must be an ancestor of its site repository's
   `main`, its declared Worker inputs must be unchanged, and the live remote MCP
   contract must pass. This hosted deployment is independently versioned.
3. Official `mcp-publisher` 1.8.1 validation of `server.json` after checking the
   publisher binary's pinned digest.
4. One Python distribution build, strict Twine/README metadata validation, an
   isolated installed-wheel consumer with optional Workspace dependencies, and
   the current MCP consumer contract.
5. PyPI publication through GitHub OIDC and the protected `pypi` environment;
   multi-architecture GHCR publication; official MCP Registry publication after
   the Python/container jobs succeed.
6. The pinned MCP bundle packer, CycloneDX SBOM, artifact checksums, GitHub build
   attestations and release asset upload.

Useful non-publishing checks from the built distribution environment are:

```sh
python3 -m build
python3 -m twine check --strict dist/*
python3 scripts/verify_pypi_metadata.py dist/*.whl
python3 scripts/verify_published_mcp.py \
  --contract integrations/financial-evidence-mcp-current.json \
  --receipt candidate-mcp-receipt.json -- financial-evidence mcp
```

The final command must resolve to the isolated **0.1.16 installed consumer**,
not an older global installation. Test `connect --catalog`, disabled-approval
rejection and an approved synthetic profile from outside the checkout, then
independently read back the generated files and hashes. A working source import
alone is insufficient wheel acceptance.

## Publication and readback

The root release owner must review the exact final commit and complete the
signing/merge gates. Creating and pushing `v0.1.16` triggers publication; these
notes do not perform or authorize an additional mutation.

After the release workflow succeeds, independently download the actual published
wheel/source archive/MCP bundle/SBOM, verify checksums and provenance, install the
public wheel in a fresh environment, and run the versioned
`financial-evidence-mcp-v0.1.16.json` contract plus the new connection workflow.
Verify the OCI index and both supported architectures against their actual new
digests and signed source identity. Read back the exact official Registry
version; a successful publish job is not the final consumer acceptance receipt.

Only after those checks add `docs/releases/0.1.16.json` with real hashes, source
commit, workflow/attestation references and acceptance evidence. Then advance
verified public install pins, catalog release state and citation date/URL.
Keep the 0.1.15 receipt and frozen consumer checks as historical evidence; add
new checks/digests instead of overwriting history. This candidate note is not a
release receipt, marketplace receipt, uptime statement or adoption claim.
